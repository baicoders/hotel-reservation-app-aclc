HOTEL RESERVATION SYSTEM
SYSTEM DOCUMENTATION
======================

Document scope
--------------
This document describes the Laravel hotel-reservation-app as implemented in the
repository at the time of writing. It covers the application purpose, runtime
stack, user-facing functions, routes, UI structure, database schema, models,
controllers, request/response logic, seed data, assets, and testing status.
It documents current behavior; it does not imply that placeholder methods or
commented-out workflows are production-ready.


1. SYSTEM OVERVIEW
------------------

The application is a server-rendered hotel reservation system with two main
experiences:

1. Public guest experience:
   - View the landing page.
   - Search rooms by check in and check out dates; only rooms free for the
     whole stay and not in maintenance are listed.
   - View room details and every photo.
   - Book a room for the chosen dates; the total is the nightly rate times
     the nights.
   - Receive a printable receipt with a confirmation number.

2. Authenticated staff experience:
   - Sign in and sign out.
   - View a dashboard with totals and the latest reservations, rooms and
     guests.
   - List, filter and inspect reservations, including their payment.
   - Change reservation status (check in, check out, cancel).
   - List, search, inspect and delete guests.
   - List, search, filter, inspect, create, edit, and delete rooms.
   - Upload room photos when creating or editing a room.

The application is built with Laravel 12, PHP 8.2+, Eloquent ORM, Blade
templates, Tailwind CSS, and Vite. It uses Laravel's session-based web
authentication middleware. There is no separate API layer or JavaScript
single-page application.

3. USER ROLES AND ACCESS CONTROL
--------------------------------

Guests are not required to create an application account. They use public
routes to browse and reserve a room. Guest details are saved in the guests
table during booking.

Staff use the users table and Laravel's auth middleware. Every route inside
the staff route group requires an authenticated user:
- /dashboard
- /reservations and reservation detail/status routes
- /guest and guest detail/delete routes
- /rooms and room management routes

Authentication details:
- The login form accepts "username" and "password"; both are required.
- The username is matched against users.name, not users.email.
- /login is wrapped in the guest middleware, so a signed in user who opens it
  is sent to /dashboard.
- On successful login, the session is regenerated, any guest receipt kept in
  that browser session is cleared, and the user is redirected to the
  intended URL or dashboard.
- On failure, the user is returned to the login form with the error under the
  Username field; only the username is kept.
- Login attempts are not rate limited (see section 13).
- Logout invalidates the session and regenerates the CSRF token before
  redirecting to /login.
- Blade forms use Laravel CSRF tokens where applicable.


4. ROUTES AND REQUEST FLOWS
---------------------------

Public routes:

GET  /                                      Renders home.blade.php.
GET  /home                                  Renders the same home page.
GET  /login                                 Shows authentication.login.
POST /login                                 Authenticates a staff user.
POST /logout                                Logs out the authenticated user.
GET  /search-room                           Lists rooms free for the stay.
                                             Query: check_in, check_out
                                             (default today and tomorrow),
                                             type, sort (price_asc,
                                             price_desc), page.
GET  /guest/rooms/details/{room_id}         Shows guest-facing room details
                                             for the check_in and check_out
                                             query dates.
GET  /guest/rooms/reserve                   Shows the booking form. room_id is
                                             required (else redirect to
                                             /search-room); check_in and
                                             check_out prefill the stay.
POST /guest/rooms/booking-room              Validates and creates the guest
                                             (reused by email), reservation
                                             and payment in one transaction,
                                             then redirects to the receipt.
GET  /guest/receipt                         Shows the receipt kept in the
                                             visitor's session (15 minutes).
POST /guest/receipt/clear                   Clears that receipt and goes home
                                             or to the room browser.
GET  /up                                    Laravel health check.

Authenticated staff routes:

GET    /dashboard                           Staff dashboard.
GET    /reservations                        Reservation list, 15 per page.
                                             Query: status, guest, room, date.
GET    /reservations/details/{id}            Reservation, guest, room, payment
                                             detail page.
POST   /reservations/update-status/{id}     Validates and changes reservation
                                             status, its dates and the room
                                             status (decision 0002).
GET    /guest                               Guest list, 20 per page. Query:
                                             query (name or email).
GET    /guest/details/{id}                  Guest details and booking history.
DELETE /guest/delete/{id}                   Deletes a guest and frees rooms
                                             they are checked in to.
GET    /rooms                               Room list, 12 per page. Query:
                                             query, status.
GET    /rooms/search                        Same list, kept for old links.
GET    /rooms/details/{id}                  Room details, photos, and every
                                             reservation with its status.
GET    /rooms/edit/{id}                     Room edit form.
POST   /rooms/update/{id}                   Validates and updates room data and
                                             adds photos.
GET    /rooms/create                        Room creation form.
POST   /rooms/record                        Creates a room and optional photos.
DELETE /rooms/delete/{id}                   Deletes a room, its reservations,
                                             payments and photo files.

There are no named route declarations for most application routes; the login
route and logout route are named.


5. PUBLIC UI AND USER WORKFLOWS
--------------------------------

Shared layouts:
- resources/views/layout/app.blade.php is the base layout. It loads
  resources/css/app.css and resources/js/app.js through Vite and the Google
  Fonts, sets the page title to "<page> | ACLC Hotel", includes the flash
  messages (components/alert, which includes components/pop-error) and the
  confirm dialog (components/modal-pop), then the page scripts section.
- Every POST form disables its submit buttons once it submits and shows
  "Saving..." or the form's data-busy-label, so a double click cannot submit
  twice. The dialog locks the form when Confirm is pressed.
- Pages that show errors under their fields declare an inline-errors section,
  which hides the corner error summary.
- resources/views/layout/guest.blade.php is the public page shell: a header
  with Rooms and Staff sign in, the page title, and a footer. The header,
  footer and receipt buttons are hidden when printing.

Home page (home.blade.php):
- Full height hero over public/aclc_building_img.jpg with the system title,
  a short description, Reserve a room (to /search-room) and Manage (to
  /dashboard), and a footer with the year, attribution and the version from
  APP_VERSION when it is set.

Room browser (guest/search-rooms.blade.php):
- Check in and check out fields (today and tomorrow by default), a room type
  filter offering only types that have free rooms, and a price sort.
- Lists rooms free for the stay in pages of 12, with a count and the stay
  summary. Bad dates show an error and fall back to tonight.
- Each card (components/room-cards) shows the room number on the brass key
  tag (components/key-tag), the type, the nightly price, an Available badge,
  the first photo or a placeholder, View details and Reserve; both links
  carry the dates.

Guest room details (guest/room-details.blade.php):
- The room's number, type, nightly price and status, a gallery of every
  photo with Previous and Next (components/room-gallery), and the chosen
  dates.
- Reserve this room opens the booking form with the dates. When the stay
  overlaps an existing one the page says the room is already booked for
  those dates; for a room in maintenance it says the room cannot be booked.

Booking form (guest/reserved-room-form.blade.php):
- Stay, guest details and payment sections beside a summary of the room,
  nightly rate, nights and total.
- The amount is read only: the server fills it with the total for the dates
  and a script updates the nights, total and amount when the dates change.
- Errors sit under their fields; every entered value is kept after an error.
  Book and pay submits to POST /guest/rooms/booking-room; Cancel returns to
  the room page with the dates.

Receipt (guest/receipt-page.blade.php):
- Shown at GET /guest/receipt after the booking redirects there. It has the
  confirmation number (reservation id as "#" and six digits), the stay, the
  room, the guest details as typed, the payment and the total paid.
- Print receipt and Save as PDF open the browser print window. Book another
  room and Done clear the receipt. It also expires after 15 minutes and is
  cleared when staff sign in on that browser.

Login and errors:
- authentication/login.blade.php shows the building beside a Username and
  Password form with the error under the field.
- errors/404.blade.php says the page was not found and links home and to
  the room browser.

7. CONTROLLERS AND CODE LOGIC
-----------------------------

AuthenticationController:
- loginUser() validates username and password, maps the username to
  users.name, regenerates the session and clears any guest receipt on
  success, and returns the error on the username field on failure.
- logout() logs out, invalidates the session, regenerates the CSRF token and
  redirects to /login.

ManageController:
- dashboard() counts rooms, available rooms, open reservations and guests,
  and loads the latest reservations (joined to guests and rooms), guests,
  rooms, and rooms that are not available.

RoomController:
- index() and search(): the staff list with the grouped number or type
  search (LIKE wildcards escaped), the status filter and pagination.
- listRooms(): the public browser. stayDates() validates the query dates;
  rooms not in maintenance with no overlapping stay are listed.
- store() and update(): validate the room fields and photos together, then
  save the room and store photos through uploadPhoto().
- show(): the room, its photos and every reservation for the staff page.
- reserveRoom(): the public room page, with an overlap check for the dates.
- destroy(): deletes the room row, then its photo files.

GuestController:
- index(): paginated guests with their reservation counts and search.
- show(): the guest and their reservations joined to rooms, with aliased
  room columns so reservation ids and statuses stay correct.
- destroy(): in one transaction, frees rooms the guest is checked in to
  (unless another guest is checked in or the room is in maintenance), then
  deletes the guest; reservations and payments cascade.
- create(), store(), edit(), and update() are placeholders.

ReservationController:
- index(): the staff list with the status, guest, room and date filters.
- reserveRoomForm(): requires a single room_id, refuses rooms in
  maintenance, and computes the nights and total from the kept input or the
  query dates.
- reserveRoom(): validates the booking, checks the total, and in one
  transaction locks the room, rejects overlaps, reuses or creates the guest,
  and creates the confirmed reservation and the paid payment. It stores the
  receipt in the session and redirects to /guest/receipt.
- receipt() and clearReceipt(): show or clear that session receipt.
- show(): the reservation with its guest, room and first payment.
- update(): changes the status, the stay dates and the room status in one
  transaction (section 9).
- create(), store(), edit(), and destroy() are placeholders.

Model logic:
- Room: mass assignable number, type, nightly price and status; firstPhoto()
  and reservations() relations.
- RoomModel: the rooms_photos table (room_id, photo_path).
- Guest: mass assignable full name, email, phone number and address;
  reservations() relation.
- Reservation: mass assignable room_id, guest_id, dates and status; the
  overlapping() scope.
- Payment: mass assignable reservation_id, amount, payment date, method and
  status.
- User: Laravel's Authenticatable model with hashed passwords.


8. DATABASE SCHEMA
------------------

Application tables from
database/migrations/2025_10_03_030144_hotel_reservations_tables.php:

rooms
- id: auto-increment primary key.
- rm_number: string, unique room number.
- rm_type: string room type.
- rm_price_per_night: decimal(8,2).
- status: string, default "available".
- created_at, updated_at.

rooms_photos
- id: auto-increment primary key.
- room_id: foreign key to rooms.id, cascade on room deletion.
- photo_path: stored public-disk path.
- created_at, updated_at.

guests
- id: auto-increment primary key.
- full_name: string.
- email: string, unique.
- phone_number: nullable string.
- address: nullable string.
- created_at, updated_at.

reservations
- id: auto-increment primary key.
- room_id: foreign key to rooms.id, cascade on room deletion.
- guest_id: foreign key to guests.id, cascade on guest deletion.
- check_in_date: date.
- check_out_date: date.
- status: string, default "pending".
- created_at, updated_at.

payments
- id: auto-increment primary key.
- reservation_id: foreign key to reservations.id, cascade on reservation
  deletion.
- amount: decimal(8,2).
- payment_method: string.
- status: string, default "pending".
- payment_date: date.
- created_at, updated_at.

Resolved implementation mismatch:
- ReservationController::reserveRoom() no longer passes guest_id to
  Payment::create(); payments relate to guests only through their
  reservation, as the schema defines.

Relationships defined on the models:
- Room hasMany reservations and hasOne firstPhoto (rooms_photos).
- Guest hasMany reservations.
- Reservation has an overlapping($checkIn, $checkOut) query scope: pending,
  confirmed and checked_in stays that start before the check out and end
  after the check in. The booking, the room browser and the room page all
  use it.

Laravel framework tables:
- users: id, name, unique email, email verification timestamp, password,
  remember token, timestamps.
- password_reset_tokens: email primary key, token, created_at.
- sessions: session id, optional user_id, IP address, user agent, payload,
  last activity, with indexes where defined.
- cache and cache_locks: framework cache storage.
- jobs, job_batches, and failed_jobs: queue storage.

The down() method in the hotel migration drops rooms, reservations, guests,
payments, and amenities. Because rooms_photos is not explicitly dropped in
that method, rollback ordering relies on the database's handling of the
foreign key and should be reviewed if migrations are rolled back.

Amenities:
- The amenities table has id, name, nullable description, decimal price
  defaulting to zero, and timestamps.
- No active model, controller, route, or view currently uses amenities.


9. VALIDATION, STORAGE, AND DATA RULES
--------------------------------------

Room creation:
- roomNumber is required, string, max 13 characters, and unique.
- roomType is required, string, max 255 characters.
- roomPrice is required, numeric, minimum 0, maximum 99999.99, with up to
  two decimal places (100 and 100.50 are both accepted).
- status is optional, one of available, unavailable or maintenance; defaults
  to available.
- Photos are validated with the room fields, so an invalid photo saves
  nothing.

Room update:
- roomType, roomPrice, status and photos use the same rules; new photos are
  added to the existing ones.
- room number is not changed by the update action.

Room photos:
- Accepted types are jpeg, png, jpg, and gif, checked by file content.
- Maximum file size is 4096 KB.
- Files are saved to the public filesystem disk in room-photos under a random
  name whose extension comes from the file content, not the uploaded name.
- Metadata is stored in rooms_photos. Deleting a room deletes its files.

Guest booking:
- room_id, check_in_date, check_out_date, name, email, phone, address,
  amount, payment_method, and payment_date are required.
- check_in_date is today or later; check_out_date is after check_in_date;
  a stay is at most 30 nights (ReservationController::MAX_NIGHTS).
- email must be a valid email address; phone is at most 30 characters.
- payment_method is one of credit_card, debit_card, paypal or cash;
  payment_date is today or earlier.
- The amount must equal the nightly rate times the nights, to the cent.
- Rooms in maintenance cannot be booked. Inside the booking transaction the
  room row is locked and the stay is refused if it overlaps a pending,
  confirmed or checked_in reservation of that room.
- A guest is reused by email; a returning guest's stored details are not
  overwritten from the public form.
- A booking does not change the room status (decision 0002).

Reservation status:
- Allowed values are pending, confirmed, checked_in, checked_out, and
  cancelled.
- checked_in sets the room to unavailable (unless in maintenance) and the
  check in date to today; checked_out sets the check out date to today.
- checked_out, cancelled, or moving a stay back from checked_in frees the
  room when it is unavailable and no other reservation of it is checked in.
- The change and the room update run in one transaction with the room row
  locked.

13. CURRENT LIMITATIONS AND FOLLOW-UP AREAS
-------------------------------------------

Resolved by the UI/UX overhaul (branch feature/ui-ux-overhaul):
- Bookings use chosen check in and check out dates instead of one night.
- The booking runs in one transaction that locks the room and rejects
  overlapping stays, so a room cannot be double booked.
- The amount must equal the calculated total exactly.
- The payment payload no longer references guest_id.
- Check out and cancellation re-open the room (decision 0002).
- The dashboard query joins guests and rooms for the names it shows.
- Deleting a room removes its photo files.
- The old multi step booking templates and commented methods are removed.
- The test suite covers the core workflows (section 12).

Still open:
- Guest create/edit/update actions are placeholders.
- Reservation create/edit/store/destroy actions are placeholders.
- Amenities are schema-only and have no user-facing functionality.
- Authorization is currently binary authenticated/not authenticated; there
  are no staff roles or permissions beyond login.
- No confirmation email is sent; the receipt page is the only confirmation.
- resources/views/welcome.blade.php (Laravel's default page) is unused.
- config/database.php uses PDO::MYSQL_ATTR_SSL_CA, deprecated in PHP 8.5, so
  test runs in the Sail container (PHP 8.5) print a deprecation notice.

Waiting on a decision from the owner:
- The app timezone is UTC, so staff see UTC times and "today" in booking
  rules is the UTC date. config/app.php hard-codes 'timezone' => 'UTC';
  change it to the hotel's zone (or make it read an env value).
- POST /login has no rate limit; choose an attempt limit.
- Sessions, which briefly hold a guest's receipt, are stored unencrypted in
  the sessions table; SESSION_ENCRYPT=true would encrypt them.


14. OPERATIONAL STARTUP
-----------------------

Typical local setup:

1. Install PHP dependencies:
       composer install
2. Install frontend dependencies:
       npm install
3. Configure .env and database settings.
4. Generate the application key if required:
       php artisan key:generate
5. Run migrations and seed development records:
       php artisan migrate --seed
6. Create the public storage link:
       php artisan storage:link --force
7. Start the application:
       php artisan serve
   In a separate terminal, run:
       npm run dev

Docker (Laravel Sail) setup, used for development on Windows:

1. Install PHP dependencies without a local PHP:
       docker run --rm -v "${PWD}:/app" -w /app composer:latest install --ignore-platform-reqs
2. Copy .env.example to .env and set DB_HOST=mysql, DB_USERNAME=sail,
   DB_PASSWORD=password, APP_URL=http://localhost:8080, APP_PORT=8080,
   VITE_PORT=5174, WWWUSER=1000 and WWWGROUP=1000 (the Sail image build
   needs both; MySQL refuses root as MYSQL_USER).
3. Start the containers:
       docker compose up -d --build
4. Run the Laravel steps inside the app container:
       docker compose exec laravel.test php artisan key:generate
       docker compose exec laravel.test php artisan migrate --seed
       docker compose exec laravel.test php artisan storage:link --force
5. Build frontend assets (npm run build) and open http://localhost:8080.

docker/php/opcache.ini caches compiled PHP without timestamp checks, because
those checks through the Windows file mount made pages take seconds. After
editing PHP or Blade files, restart the app container:

       docker compose restart laravel.test

The exact database and service values should be read from compose.yaml and
the active .env before deployment.
