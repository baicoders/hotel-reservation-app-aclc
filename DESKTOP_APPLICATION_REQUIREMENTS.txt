HOTEL RESERVATION SYSTEM
DESKTOP APPLICATION IMPLEMENTATION REQUIREMENTS
================================================

Purpose
-------
This document translates the current Laravel web application into a
framework-neutral plan for creating an equivalent desktop application.
It identifies the software components, screens, database, workflows, rules,
security controls, packaging needs, and testing work required to reproduce
the documented system in a desktop framework such as:

- C#/.NET with WPF or WinUI
- Java with JavaFX
- Python with PySide/PyQt
- Electron with a local service/database
- Tauri with a Rust backend and desktop web UI

The implementation should preserve the existing hotel reservation behavior
unless a requirement below explicitly recommends correcting a documented
limitation.


1. RECOMMENDED DESKTOP ARCHITECTURE
-----------------------------------

Use a layered desktop architecture:

1. Presentation layer
   - Windows, pages, dialogs, navigation shell, forms, tables, cards, and
     notifications.
   - Handles user interaction and display state only.

2. Application/service layer
   - Authentication service.
   - Room service.
   - Guest service.
   - Reservation service.
   - Payment service.
   - Dashboard/reporting service.
   - Coordinates validation, transactions, and screen data.

3. Domain/model layer
   - User, Room, RoomPhoto, Guest, Reservation, Payment, and Amenity models.
   - Enumerations for room status, reservation status, payment status, and
     payment method.
   - Domain validation and relationships.

4. Data access layer
   - Repository or data-access classes for SQLite or another selected
     database.
   - Parameterized queries or a desktop ORM.
   - Migration/versioning support.

5. Infrastructure layer
   - Password hashing.
   - File storage for room images.
   - Logging.
   - Configuration.
   - Backup and restore.
   - Application update/packaging support.

For a single-computer installation, a local SQLite database is the simplest
replacement for the Laravel database. For multiple staff computers, use a
central PostgreSQL/MySQL/SQL Server database and expose the application
through a secured service/API instead of allowing direct shared-file access.

5. DATA MODEL AND DATABASE REQUIREMENTS
----------------------------------------

Create database migrations for the following tables.

users
- id: integer primary key.
- name: required string; unique if username uniqueness is required.
- email: required string; unique.
- email_verified_at: nullable datetime.
- password_hash: required string.
- remember token or equivalent only if persistent login is implemented.
- created_at and updated_at.

rooms
- id: integer primary key.
- rm_number: required string; unique.
- rm_type: required string.
- rm_price_per_night: required decimal(8,2), non-negative.
- status: required enum/string; default available.
- created_at and updated_at.

rooms_photos
- id: integer primary key.
- room_id: required foreign key to rooms.id.
- photo_path: required string.
- created_at and updated_at.
- Delete behavior: cascade metadata when a room is deleted.

guests
- id: integer primary key.
- full_name: required string.
- email: required unique string.
- phone_number: nullable string.
- address: nullable string.
- created_at and updated_at.

reservations
- id: integer primary key.
- room_id: required foreign key to rooms.id.
- guest_id: required foreign key to guests.id.
- check_in_date: required date/datetime.
- check_out_date: required date/datetime.
- status: required enum/string; default pending.
- created_at and updated_at.

payments
- id: integer primary key.
- reservation_id: required foreign key to reservations.id.
- amount: required decimal(8,2), non-negative.
- payment_method: required string/enum.
- status: required enum/string; default pending.
- payment_date: required date.
- created_at and updated_at.

amenities
- id: integer primary key.
- name: required string.
- description: nullable text.
- price: decimal(8,2), default zero.
- created_at and updated_at.

Framework/support tables:
- password reset tokens if password reset is supported.
- sessions only if session persistence is needed.
- application settings/configuration table if settings must be editable.
- audit_logs for staff actions in a production desktop application.

Recommended indexes:
- rooms.rm_number unique index.
- rooms.status index.
- rooms.rm_type index.
- guests.email unique index.
- reservations.room_id index.
- reservations.guest_id index.
- reservations.status index.
- reservations.check_in_date index.
- reservations.check_out_date index.
- payments.reservation_id index.

Important schema correction:
- Do not add guest_id to payments unless the business model explicitly
  requires it. The documented web code attempts to save guest_id, but the
  current payments schema only relates payments to reservations.


6. DOMAIN ENUMS AND BUSINESS RULES
-----------------------------------

Room status:
- available
- unavailable
- optionally maintenance or inactive

Reservation status:
- pending
- confirmed
- checked_in
- checked_out
- cancelled

Payment status:
- pending
- paid
- failed
- refunded

Required rules:
- Only available rooms may be shown in the public room browser.
- A room cannot be booked if it is unavailable.
- Room number must be unique.
- Room price must be non-negative and stored with two decimal places.
- Guest email must be valid and unique.
- Existing guests should be reused by email during booking.
- A booking must have a valid room, guest, dates, and payment amount.
- Payment amount should normally equal the calculated reservation total.
- Check-out must be after check-in.
- A reservation must reference an existing room and guest.
- A payment must reference an existing reservation.
- Status changes must be restricted to known values.
- Check-in sets the check-in date/time.
- Check-out sets the check-out date/time.
- Cancellation should release the room when no other active reservation
  conflicts with it.
- Deleting a room should remove its database photo metadata and either remove
  or archive the physical image files.
- Destructive actions require confirmation.

Recommended improvement over the current web behavior:
- Replace the hard-coded one-night stay with selected check-in/check-out
  dates.
- Calculate total price as nightly rate multiplied by number of nights,
  plus any selected amenities.
- Use a single database transaction for guest, reservation, payment, and room
  status changes.
- Recheck room availability inside the transaction to prevent double booking.


7. SERVICE AND CODE LOGIC REQUIREMENTS
---------------------------------------

AuthenticationService:
- authenticate(username, password).
- Hash verification using Argon2id or bcrypt.
- Establish current authenticated user.
- clearSession/logout().
- Return explicit invalid-credential errors.

RoomService:
- listAvailableRooms().
- listRooms(limit, filters).
- searchRooms(query).
- getRoom(id).
- createRoom(data, imageFiles).
- updateRoom(id, data).
- deleteRoom(id).
- getRoomPhotos(id).
- validateRoomInput(data).
- Store image files in an application-managed directory, not an arbitrary
  user-selected location.

GuestService:
- listGuests(limit).
- getGuest(id).
- findByEmail(email).
- createOrReuseGuest(data).
- getGuestReservations(id).
- deleteGuest(id).
- Define whether deletion is blocked when reservations exist or cascades.

ReservationService:
- listReservations(filters).
- getReservationDetails(id).
- createReservation(bookingData).
- updateStatus(id, status).
- calculateTotal(room, dates, amenities).
- checkAvailability(roomId, dates).
- set check-in/check-out dates when status changes.

PaymentService:
- createPayment(reservationId, paymentData).
- validateAmount().
- updatePaymentStatus().
- retrieveReservationPayment().
- Never store raw card numbers, CVV, or other sensitive payment credentials.

DashboardService:
- getLatestReservations(5).
- getLatestGuests(5).
- getLatestRooms(5).
- Return view models that already contain display labels required by the UI.

Validation service:
- Required-field validation.
- Email validation.
- Date and date-range validation.
- Decimal/currency validation.
- File extension, MIME type, and size validation.
- Duplicate room/guest checks.


8. FILE AND IMAGE STORAGE
-------------------------

Create an application data directory such as:

Windows:
  %LOCALAPPDATA%\HotelReservationSystem\data\

Suggested subdirectories:
- database\
- room-photos\
- receipts\
- backups\
- logs\

Requirements:
- Generate collision-resistant photo filenames.
- Validate file type and size before copying.
- Store only relative paths in the database.
- Display missing-image placeholders when a file is unavailable.
- Keep database writes and file operations coordinated.
- Clean up a copied image if database insertion fails.
- Provide a backup option that includes both the database and room photos.


9. DESKTOP NAVIGATION AND STATE
-------------------------------

Global application state:
- Current authenticated staff user.
- Selected room.
- Selected reservation.
- Current navigation page.
- Notification queue.
- Database connection/service status.

Navigation rules:
- Open Home without authentication.
- Allow public room browsing and booking without staff login.
- Require authentication before opening dashboard, room management, guest
  management, and reservation management.
- Return to login when logout is selected.
- Clear sensitive form state after a successful booking or logout.
- Disable staff actions when the database is unavailable.

Use view models or presentation models so database entities are not directly
responsible for UI formatting or control state.


10. ERROR HANDLING AND LOGGING
------------------------------

Display actionable errors for:
- Invalid login.
- Missing or invalid form fields.
- Room not found.
- Guest/reservation/payment not found.
- Room already unavailable.
- Duplicate room number or guest email.
- Database connection/query failure.
- Image selection, copy, or deletion failure.
- Receipt export/printing failure.

Logging requirements:
- Log unexpected exceptions with timestamp and stack trace.
- Log failed database operations without passwords or payment secrets.
- Log staff actions such as room deletion and reservation status changes.
- Show users a safe message instead of raw exception details.
- Never silently continue after a failed reservation or payment insert.


11. SECURITY REQUIREMENTS
-------------------------

- Hash passwords using Argon2id or bcrypt; never store plaintext passwords.
- Use parameterized SQL or a safe ORM.
- Validate all desktop form input before persistence.
- Restrict staff screens to authenticated staff users.
- Add role/permission checks if more than one staff role is introduced.
- Protect local database and photo directories with appropriate OS file
  permissions.
- Do not store card numbers, CVV, or sensitive payment credentials.
- Mask sensitive values in logs.
- Lock or timeout inactive staff sessions where appropriate.
- Protect backups with encryption and access controls.
- Validate image content and extension to reduce malicious-file risk.
- Sign packaged installers and application updates when possible.


12. REPORTING, PRINTING, AND EXPORT

Recommended desktop features:

- Booking form validation.
- Successful booking and receipt.
- Room CRUD.

Acceptance scenarios:
1. Staff logs in and sees the dashboard.
2. Guest views available rooms and selects one.
3. Guest submits valid details and receives a receipt.
4. The room becomes unavailable after booking.
5. Staff views the reservation and payment.
6. Staff changes status to checked_in and checked_out.
7. Staff searches, edits, and deletes a room.
8. Staff opens a guest and sees booking history.
9. Invalid and conflicting operations produce clear errors.


15. BUILD, PACKAGING, AND DEPLOYMENT
------------------------------------

Development build:
- Run the selected framework's restore/install command.
- Run database migrations.
- Create local data directories.
- Run unit, integration, and UI tests.
- Start the desktop application in debug mode.

Production build:
- Compile in release mode.
- Include migrations and first-run setup.
- Include required runtime dependencies or use a self-contained build.
- Bundle icons, branding, default styles, and fallback images.
- Configure a writable application-data directory.
- Create an installer and uninstaller.
- Sign the application package where possible.
- Include a version number and release notes.

Deployment checklist:
- Verify database initialization.
- Verify image directory permissions.
- Verify backup/restore.
- Verify receipt printing/export.
- Verify staff login.
- Verify no development credentials are enabled.
- Verify logs do not expose secrets.
- Verify upgrade migration behavior.


16. IMPLEMENTATION PHASES
-------------------------

Phase 1 - Foundation:
- Choose desktop framework.
- Create project and layered architecture.
- Add configuration, logging, database connection, and migrations.
- Build application shell and navigation.

Phase 2 - Identity:
- Implement users table and password hashing.
- Build login/logout.
- Add authenticated route/page guards.

Phase 3 - Rooms:
- Implement rooms and rooms_photos.
- Build room list, search, detail, create, edit, delete, and image handling.

Phase 4 - Guest booking:
- Build available-room browser and detail page.
- Build booking form and validation.
- Implement guest reuse, reservation transaction, payment, and receipt.

Phase 5 - Staff operations:
- Build dashboard.
- Build reservation list/detail/status management.
- Build guest list/detail/delete and booking history.

Phase 6 - Reliability:
- Add transactions, conflict detection, audit logging, backups, and cleanup.
- Resolve the documented schema/controller mismatches.

Phase 7 - Quality and release:
- Add automated tests.
- Add printing/export.
- Package installer.
- Perform acceptance testing and security review.


17. DEFINITION OF DONE
----------------------

The desktop implementation is complete when:
- Staff can securely log in and log out.
- Guests can browse only available rooms.
- Room details and photos display correctly.
- A valid booking creates one guest, reservation, and payment consistently.
- A booked room cannot be double-booked.
- Receipt data matches persisted reservation/payment data.
- Staff can manage rooms, reservations, and guests.
- Reservation status transitions update dates correctly.
- Database and image storage are backed up together.
- Invalid input and system failures are visible and actionable.
- Automated tests cover the core workflows.
- The application installs, starts, upgrades, and uninstalls reliably.
- Production builds contain no development credentials or debug behavior.
